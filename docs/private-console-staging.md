# Churn Lab v1.9 — private staging browser console

**Experimental / default disabled. No public launch, user signup, paid cloud
database, real OIDC connection or real customer data.**

v1.9 provides a responsive, accessible Spanish-language UI to operate the
**existing v1.8 staging API** with synthetic accounts and organizations.
There is no new persistent storage, migration, third-party API or mail service.

## Private URLs

- `GET /saas/v3/console`: management page
- `GET /saas/v3/console.js`: self-hosted browser controller
- `GET /saas/v3/console.css`: self-hosted responsive styling
- `GET /saas/v3/organizations/list`: live issuer/subject-scoped
  list of organizations from existing v1.7 membership lookup

**All four endpoints require** `CHURN_SAAS_MANAGEMENT_ENABLED=1` and a
valid `CHURN_SAAS_LOGIN_ENABLED=1` browser session with the existing
OIDC/PostgreSQL configuration. They serve **404** by default or **401**
without an authenticated session. The JS and CSS are placed in
`private_assets`, NOT in the public `/assets` mounted static directory.

Once a private OIDC provider is connected, open `/saas/v3/login`, sign
in with Authorization Code + PKCE and use the link on `Mis empresas`
to open `/saas/v3/console`. No OIDC accounts are configured by this PR.

## UI features and ownership

- Switch between the signed-in identity's own active organizations.
- Create a synthetic organization and become its first owner.
- Redeem a one-time invitation code, generated by another owner.
- As owner: list organization members, change roles, revoke access,
  generate viewer/analyst codes. Backend always checks membership/ownership,
  rejects unauthorized access and prevents removing the final owner.
- Invite code appears only after successful issuance, remains visible
  *temporarily in the current DOM*, is cleared when switching
  organizations or leaving the page. It is never written to logs, analytics,
  browser storage or the database in plaintext.
- The provider's OIDC subject may be a technical identifier, not a friendly
  display name. The console does not expose user emails or profiles.

The page uses native forms, keyboard-operable controls, text status
announcements, mobile layout, self-hosted JS/CSS and no remote resources.
Dynamic names, roles, subjects and invitation codes are inserted with DOM
`textContent` rather than HTML. Browser JSON mutations use same-origin
cookies and the existing strict Origin check; the app's per-IP rate limit
and bounded request bodies remain active. `Cache-Control: no-store` is
set on private page, data and assets.

## Test and release policy

GitHub Actions `Optional SaaS security integration` includes new
`test_staging_console.py`, which checks default-off 404s, missing-session
401s, tampering rejection, authenticated assets, no templated identity
leakage, self-only organization JSON and owner/member isolation in an
ephemeral PostgreSQL 16 DB. The public Docker smoke checks the console and
its assets are **not accessible** without staging flags.

The existing CI checks validate training, prediction, Docker, dependencies
and the public demonstration. Browser visual QA tests the **public demo**
and does not constitute a real browser test of the OIDC console with a
hosted identity provider; that requires separate private staging setup.

## Not ready for real customers

No provider-admin integration, user registration, persistent revocable
sessions, MFA, verified email-bound invitations, mail delivery, invite
revocation, friendly user directory, billing, production tenant quotas,
audit logs or completed privacy/security review. A private isolated HTTPS
staging host, actual OIDC provider and PostgreSQL configuration are still
needed to exercise the full browser workflow. **Never enable the feature
flags on the public portfolio deployment or enter real customer data.**
